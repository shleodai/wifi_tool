# WPA2 计算性能测试：Windows RTX 3060 / Mac / RHEL 8

本目录独立于已有的破解工具。当前只有只读环境检查，不安装依赖、不联网、不启动 benchmark，也不改系统配置。检查脚本仅依赖 Python 标准库，语法兼容 Python 3.6+；外部命令缺失或失败会记录在 JSON 中。

当前目标见 [OBJECTIVE.md](OBJECTIVE.md)：优先在 Windows 游戏本的 RTX 3060 上评估 WPA2 模式 22000 的实际吞吐，约 50% 平均负载为目标，优先保证电脑交互流畅。上传仓库已获授权；运行新的重负载测试仍须先确认方案。

## Windows 游戏本：clone 后从这里开始

在 PowerShell 中运行：

```powershell
git clone https://github.com/shleodai/wifi_tool.git
cd wifi_tool
py -3 check_env.py --output windows-rtx3060-env.json
```

如果没有 `py` 但 `python` 可用，将最后一行改为 `python check_env.py --output windows-rtx3060-env.json`。

检查不需要 pip 包或管理员权限，不启动 GPU 计算。报告会包含 Windows CPU/内存/系统、显示适配器、NVIDIA 驱动与显存查询（命令可用时），以及 Python/OpenSSL。macOS/Linux 专属检查在 Windows 上可能标为不可用，这是预期行为。`nvidia-smi` 缺失不代表没有 NVIDIA GPU。

回传报告后确定 Hashcat 安装及设备选择。使用原生 Windows Hashcat，不通过 WSL 使用游戏本 GPU。官方工具下载入口为 [hashcat.net](https://hashcat.net/hashcat/)，下载或安装前先确认已有驱动与运行时；不要先安装大型 CUDA 工具链。工具解压到自己可写的目录，不提交二进制到仓库。

**待批准的 GPU 测试方案：** 从 `-w 1` 的低工作负载配置开始，使用合成测试数据和 30 秒短测；根据 GPU 监测与桌面流畅度决定是否增加计算/暂停调度。`-w 1` 不代表利用率被限制到 50%，占空比也只限制平均工作时间，无法保证瞬时占用。首次不要直接启动无限时或满载基准。

环境检查与合成 benchmark 不需要密码字典或真实握手。用户随后明确授权将指定目标的真实握手和已测试的有限候选列表放入 [artifacts/](artifacts/README.md)，供 Windows 交接使用。其余原始抓包、恢复结果和机器报告不随 GitHub 同步。

## RHEL 8：最少环境检查命令

将 `check_env.py` 复制到服务器自己的可写目录，然后在该目录运行：

```sh
python3 check_env.py --output rhel8-env.json
```

无需 sudo。文件名已存在时脚本会拒绝覆盖，可换一个名称。外部检查命令每条最多等待 5 秒；不执行 GPU 计算或密码派生。`ldconfig -p` 只读取库缓存。

JSON 包含 CPU 型号和拓扑、进程 affinity、内存、Python 与 OpenSSL、PBKDF2 可用性、cgroup v1/v2 当前组及可见父组的配额，以及 GPU 设备、驱动查询和计算库线索。crypto 包只定位、不导入；核心测试不需要它们。SSL 模块和 openssl 命令可能对应不同库，应分别保留。

请回传 `rhel8-env.json`，之后根据实际限制确定进程数与限载参数。文件含本机路径和硬件信息，可先检查再分享。当前不运行 `clinfo`、`rocminfo` 或 hashcat；GPU/runtime 线索不代表已有可用的计算设备。

## 收到检查结果后的方案

1. **容量与限载。** 结合 affinity 的 CPU 集合、cpuset 和所有可见父组的 CPU quota/period，确定可用的逻辑 CPU 容量；配额可以是小数。若限制不明，先保守使用单进程和休眠限载，明确比较口径。不能按宿主机全部核心开进程。
2. **初次约 30 秒。** CPU 时间预算初步取 `0.5 × min(可见整机逻辑 CPU 数, 有效可用容量)`，使用有界进程数与按短周期 CPU 时间预算休眠。例如有效容量仅 1 核时，用 1 个进程约 50% 占空比；nice 只改善调度优先级，不作为限载机制。限载是平均预算，短暂峰值可能更高。结合实际 CPU 时间报告是否接近目标；容器内不把可见 CPU 数宣称为真实整机容量。
3. **标准库 benchmark。** 使用 `hashlib.pbkdf2_hmac('sha1', 合成密码, 合成SSID, 4096, 32)`；独立进程、同步起点、单调时钟截止。用少量已知答案自检后计时；计时阶段保留明确的输入生成策略，避免把仅重复常量输入的结果与现有动态候选测试混为一谈。脚本检查功能缺失并给出错误，不自动安装依赖。
4. **可重复输出。** 保存输入策略、算法、迭代次数、输出长度、进程数、affinity、限载参数、环境信息、总派生次数、同步计时段墙钟时间、每个 worker 与合计 CPU 时间、启动到退出时间、派生次数/秒，以及按可见容量和有效容量分别计算的 CPU 比例。父进程 CPU 时间单列，标明采样限制；子进程异常、超时或中断不得产生成功报告。
5. **比较范围。** 只比较 PBKDF2 核心密钥派生，未包含 PTK 派生、MIC 校验、握手解析、候选规则与 I/O；这不是哈希碰撞测试。M2 的异构 CPU 核心与频率也影响结果。首轮用于观察同样约 50% 负载下的吞吐；若要比较单位 CPU 时间效率，可报告次数/合计 worker CPU 秒，但不能据此推断完整密码验证吞吐。
6. **GPU 单独讨论。** 发现 GPU 后先讨论可用权限、工具依赖及限载方案，获批后才测试。GPU 利用率不等于功耗；不能假定无管理员权限就能设置功率上限，也不能将短时分批执行视为峰值负载限制。

服务器结果除以 1,746 可表示这两次 Python 测量的吞吐比，必须同时列出负载、进程数、环境与计时口径；不称为硬件精确加速比。Hashcat 模式 22000 与 Python 核心派生测试口径不同，不直接计算精确 GPU 加速比。必要时使用同一获批脚本在两台机器重新测量。
